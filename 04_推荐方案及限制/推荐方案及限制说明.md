## 一、当前实际采用的方案

当前以本地处理为主：用 **Faster-Whisper small 完成语音识别和时间戳**，用 **sherpa-onnx 执行说话人分段、声纹提取及聚类**，再按词的时间区间把文字与说话人对齐。实时转写复用同一个本地识别模型，通过持续采音、重复识别当前窗口及更新文字来实现近实时效果。Deepgram 文件和流式 API 作为独立的云端对照通道，代码已完成，未实际调用云服务。

| 功能 | 当前使用的组件与配置 | 实际完成的工作 |
|---|---|---|
| 音频读取 | PyAV 解码，统一为16 kHz、单声道、float32 PCM | 读取录音，统一后续模型的音频格式 |
| 本地离线转写 | Faster-Whisper 1.2.1，small 模型，CTranslate2 4.4.0；默认中文 | 生成片段文字、词起止时间、词概率、识别耗时及RTF |
| 本地多人区分 | sherpa-onnx 2.0.1；pyannote segmentation 3.0 的 ONNX 模型＋中文3D-Speaker声纹模型＋聚类 | 生成匿名说话人时间轨道，再与转写词对齐 |
| 本地实时转写 | sounddevice采音＋独立采集线程与队列＋Faster-Whisper重复识别 | 输出同一片段的partial修订和final，保存录音与事件日志 |
| 云端文件转写 | Deepgram Nova-3；`language=zh-CN`、`diarize_model=latest` | 已编写上传、原始响应保存、词时间与说话人字段转换代码 |
| 云端实时转写 | Deepgram WebSocket；`interim_results=true`、`endpointing=300` | 已编写音频发送、临时/最终结果接收与事件转换代码 |

本机实测环境为Python 3.11、i9-13900HX、16 GB内存和RTX 4060 Laptop 8 GB。离线识别已分别运行GPU `float16`和CPU `int8`；说话人分析采用CPU ONNX推理。GPU模式复用本机已有CUDA 12.1/cuDNN 8，因此固定了兼容该环境的CTranslate2版本。

本地模型和音频预先下载到项目目录。推理时从本地路径加载模型，并设置`local_files_only=True`；缺少模型时明确报错，不在识别过程中自动下载。本地功能不使用云端API密钥。当前提供Python命令行和PowerShell启动菜单，不包含会议纪要生成、业务界面或系统集成。

## 二、本地离线转写如何实现

处理流程为：**读取录音 → 统一音频格式 → 检测语音区间 → small模型识别 → 收集片段及词时间 → 保存原始结果与性能 → 按需进行说话人对齐 → 导出文字和字幕**。

1. 通过PyAV读取WAV、MP3、M4A等可解码录音，转换为16 kHz单声道音频；空音频和非有限数值会被拒绝。
2. 调用Faster-Whisper，开启`vad_filter=True`和`word_timestamps=True`。当前VAD配置为最短静音400 ms、语音边缘补200 ms；离线使用`beam_size=5`，不使用前一段文字作为后续识别条件。
3. 对模型返回的惰性`segments`完整迭代，提取每段的`start`、`end`、`text`以及词级`words`。时间单位均为秒，指向本次输入音频的位置；保存到小数点后三位不代表已经具有毫秒级准确度。
4. 迭代结束后停止识别计时。`elapsed_s`是ASR处理时间，`rtf=elapsed_s/音频时长`；它们排除模型加载和音频解码。另记录`pipeline_elapsed_s`，包含解码、识别和启用时的说话人分析，仍排除模型加载。
5. 保存`asr_raw.json`，再导出统一的`result.json`、可阅读的`transcript.txt`和带时间的`transcript.srt`。没有启用说话人分析时，`speaker_id`为`null`。

对应源码位于附录“项目源码”的`meeting_asr/audio.py`、`asr.py`、`offline.py`和`output.py`。原始ASR结果保留，方便区分识别错误与后续对齐造成的问题。

## 三、多人说话人区分如何实现

本功能处理的是“哪一段声音由哪个匿名说话人发出”，不识别真实姓名，也不保证不同录音中的同一编号对应同一个人。

### 1. 先获得独立的说话人时间轨道

当前使用sherpa-onnx本地管线，分段模型为`sherpa-onnx-pyannote-segmentation-3-0/model.onnx`，声纹模型来自`3dspeaker_speech_eres2net_base_sv_zh-cn_3dspeaker_16k.onnx`，在项目内保存为`speaker-embedding.onnx`。这是一条ONNX推理路线，没有运行完整的pyannote.audio Community-1管线。

分段模型分析语音活动和局部说话人，声纹模型提取声音特征，再通过聚类归并发言。命令行及主实验默认采用自动估计人数、聚类阈值0.8；已知人数时可传入`--speakers`。按说话人首次出现的顺序生成`SPEAKER_00`、`SPEAKER_01`等编号，原始时间轨道保存到`diarization_raw.json`。

### 2. 再把识别文字与时间轨道对齐

识别与说话人分析是两条独立结果，需要按时间连接，不能简单把整段文字都分配给第一个发言人。当前实现逐词计算该词与各说话人轨道的时间交集，并合并同一说话人的重叠轨道，避免重复计算覆盖长度。

具体归属规则为：

- 最多覆盖该词的说话人，其覆盖比例达到50%，且其他说话人覆盖比例都低于20%时，赋予该说话人编号。
- 最大覆盖不足50%时，输出`null`，记录`insufficient_speaker_coverage`。
- 第二个说话人的覆盖达到20%时，视为交叠或边界不明确，输出`null`，记录`overlap_or_speaker_boundary`。
- 词时间长度为0时，输出`null`，记录`zero_duration_word`；没有词时间时也不强行分配说话人。

这里的`speaker_coverage`是时间覆盖比例，不是经过校准的声纹置信度。相邻词的说话人改变，或词间间隔超过1秒时，拆成新的文字片段。这样能保留发言切换，也会把部分不明确的边界单独输出为未知标签。

对应源码为`meeting_asr/diarization.py`。该模块目前是离线功能；实时事件没有同步运行声纹追踪，实时日志中的`speaker_id`保持`null`。如需实时会话的说话人结果，应在结束后对保存的`captured.wav`再次执行离线转写及说话人分析。

## 五、本地实时转写如何实现

实时功能是基于Faster-Whisper的**近实时窗口识别**，不是该模型原生的逐字流式解码。它支持两种输入：sounddevice麦克风持续采集，以及本地录音按墙钟速度逐块输入。两者使用相同的后续识别及事件处理逻辑。

### 1. 持续采集与识别解耦

独立采集线程约每100 ms生成一块音频，进入有界队列；识别线程持续接收这些块并累积当前片段。麦克风优先采集16 kHz单声道，不支持时尝试设备默认采样率并重采样。实际送入引擎的音频同时保存为`captured.wav`，方便事后离线复核。

实时输入队列最多容纳600块，约60秒音频。如果识别长期跟不上采集，程序记录溢出并停止输入，不能把不完整结果当作完整成功。文件的`--no-pace`加速调试模式可等待识别线程，但该模式不能用于报告真实实时延迟。

### 2. 判断片段开始、更新和结束

当前以每块音频的RMS能量判断是否有声，阈值为0.008，保留通常约300 ms的前置音频，减少漏掉开头的风险。片段内每积累约1.5秒新音频，重新识别当前窗口，使用较快的`beam_size=1`；识别调用内部仍启用Faster-Whisper的VAD。外层能量起止规则与模型内部VAD不是同一个环节。

正常更新输出`partial`。检测到连续约0.8秒低能量、当前窗口达到最长12秒，或输入结束时，再次识别并输出`final`。最长窗口触发切段时保留0.6秒音频作为后续上下文，并把词时间换算到整段录音的绝对位置；已经提交过的时间范围中的词不会再次追加。

这里的final表示本程序已结束该片段的识别，不表示内容已经人工校对正确，也不表示模型之后永远不会给出不同文字。当前代码不会用事后离线结果自动改写已发出的final；离线复核应作为另一份结果使用。

### 3. 如何记录过程

每次有效文字更新写入`events.jsonl`并立即刷新，记录片段ID、状态、文字、音频推进位置、本地事件时刻、推理耗时、修订次数等。最终片段另外汇总到`result.json`、TXT和SRT；延迟分布、队列/采音异常汇总到`summary.json`。

对应源码为`meeting_asr/realtime.py`。窗口长度、更新间隔、能量阈值和停顿时长均可通过参数调整，但本轮报告对应的是上述已实际运行配置。

## 六、实时文字如何变化

向06提供[完整实时日志](../03_实时转写记录/06_实时文字更新记录.jsonl)、[文字变化说明](../03_实时转写记录/06_实时文字变化说明.md)和该目录中的《实时延迟与修订统计.json》。配套录音是附录“测试录音及参考”的`E.wav`。

下面是E样本真实运行中同一片段的全部三次事件摘录，保留原始文字和时刻：

```jsonl
{"segment_id":"live_00001","state":"partial","text":"甚至出现交流","audio_time":2.1,"capture_end":2.1516,"emitted_at":2.9127,"revision_count":0,"text_change_count":0}
{"segment_id":"live_00001","state":"partial","text":"甚至出现交易几乎停滞的情","audio_time":3.6,"capture_end":3.6524,"emitted_at":3.8274,"revision_count":1,"text_change_count":1}
{"segment_id":"live_00001","state":"final","text":"甚至出现交易几乎停滞的情况","audio_time":4.7,"capture_end":4.7521,"emitted_at":4.9651,"revision_count":1,"text_change_count":2}
```

这三行不是三次发言。它们共享`live_00001`：首次识别成“交流”，下一次利用新增音频把该位置修订为“交易”并续写，最后补齐“情况”并确认片段结束。界面或下游程序应按片段ID维护记录，而不是将三行文字拼接。

建议06按以下逻辑消费已有事件：

1. 第一次收到某个`segment_id`时建立一条记录。
2. 收到同一ID的`partial`时，用新的`text`替换该条记录；既可能增加文字，也可能修改或缩短已有文字。
3. 收到该ID的`final`时，仍以本次`text`覆盖此前临时文字，再将记录标记为稳定。
4. 不同ID再建立新记录；离线`s00001`和实时`live_00001`不是可以直接一一对应的编号。

`revision_count`统计发生回改的次数，不把单纯在末尾续写视为回改；`text_change_count`还统计正常续写。final是事件状态，不是“识别准确率100%”的标识。当前本地实时事件没有可靠的实时说话人标签，06应允许`speaker_id=null`。

### 实时延迟应如何解释

| 字段/指标 | 计时口径 |
|---|---|
| `audio_time` | 音频已经推进到的位置，单位为秒 |
| `capture_end` | 最近输入块进入队列的本地时刻，相对本次引擎启动计时；麦克风取回调到达时间 |
| `emitted_at` | 识别事件返回时的本地时刻，相对同一次引擎启动计时 |
| `capture_to_result_s` | 最近输入块到结果返回的时间，包含排队及识别，未包含此前积累窗口的等待 |
| `audio_start_to_result_s` | 从当前片段音频开始到结果返回，包含窗口积累 |
| `last_voice_to_result_s` | 从最后检测到的有声块到结果返回，包含能量端点等待 |

这些时刻用单调时钟记录，不是日历时间；麦克风回调时刻也不等同于硬件ADC实际采样时刻。本轮123.58秒原速回放产生58个partial事件、26个final片段和25次回改；首次文字包含窗口积累后的P50为1.692秒，最后检测语音到final的P50为1.051秒。不能只取约0.1～0.2秒的“最近输入块到结果”时间宣称用户说话后立即显示文字。

## 七、云端对照方案目前实现到什么程度

云端文件接口先把输入录音转换为16 kHz单声道WAV，再通过HTTP POST上传到Deepgram。当前配置为Nova-3、中文普通话、智能格式化及说话人标记。收到响应后先保存`cloud_raw.json`，再读取词、起止时间和说话人编号，按说话人变化、词间隔和片段长度聚合为与本地相近的片段结构；服务未返回的时间或标签保留`null`。

云端实时接口通过WebSocket发送16 kHz、单声道、16 bit PCM，接收并保存原始`cloud_raw.jsonl`，同时转换为统一的partial/final事件。`is_final=true`才确认对应文字片段；`speech_final`只作为停顿标记保留，不能代替已返回的所有final片段。适配器当前根据服务返回的起始时间关联同一片段的更新，这一行为仍需真实服务测试确认。

对应源码为`meeting_asr/cloud.py`。空密钥时，在发送录音前直接返回错误，并留下请求计划；本次没有实际云端识别结果。已完成的HTTP/WebSocket测试只使用本地测试服务，验证请求格式、音频发送、原始响应保存和文字事件转换，不证明云端识别效果、线上网络延迟或费用。OpenAI文字对照是原文档的可选项，本次没有实现为核心依赖。

## 八、实测效果、已知限制及采用建议

### 当前已经得到的实测结论

| 场景 | 当前实测结果 | 能说明什么 |
|---|---|---|
| A：63.64秒清晰中文 | GPU识别2.78秒，CPU识别9.75秒；CER均约5.14% | 本机small模型可完成离线转写；GPU更快，CPU也可运行 |
| B：相同录音加入噪声和回声 | GPU识别1.66秒，CER约8.00% | 该样本加噪后文字错误增加；不能由一次耗时差异推断加噪会加速模型 |
| C：123.58秒双人轮流样本 | GPU识别3.34秒；含解码及说话人分析的整条处理约18.03秒；CER约14.29% | 已得到带时间和两位匿名说话人的实际输出，仍有边界及文字错误 |
| D：三人并有交叠 | 得到三个有文字的标签；交叠部分仍有错分、未知及漏字 | 多人流程可运行，不代表能完整分离同时讲话的人声 |
| E：123.58秒持续原速输入 | 完成partial/final更新与延迟记录；CER约19.43% | 近实时显示可用，但本次文字质量低于长录音离线识别 |

CER使用AISHELL原始人工参考，未新增人工听写；去除标点和空白等后计算，未自动折算繁简或将数字展开为汉字。时间戳仅检查了范围与顺序，没有逐词人工听音核验。D同时讲话没有唯一的串行参考，因此未计算CER。

F为AISHELL-4自然会议的连续120秒，参考标注含6名说话人。自动人数阈值0.8生成15个时间轨道标签，其中12个获得识别文字；阈值0.95得到8个轨道标签，其中6个获得文字。已知人数提示设为6时得到6个轨道标签，但只有5个获得文字。轨道人数和有文字的标签人数必须分开看，不能把“正好出现6个文字标签”当作6名说话人都正确识别的证据。

### 当前主要限制

- **识别质量**：专有名词、数字、繁简形式、噪声和短窗口边界仍可能出错；概率字段不能替代人工校对。
- **说话人区分**：自然会议容易把同一人拆成多个ID，也可能合并不同人；交叠、短应答和ASR时间误差会影响对齐。阈值探索只在同一F样本上进行，尚未证明对其他会议同样有效。说话人词中点诊断不是标准DER。
- **实时分段**：外层使用固定能量阈值，弱声或噪声可能引发漏判及错误切段；partial会回改，final也可能保留文字错误。当前没有实时说话人追踪，也没有声源分离。
- **测试覆盖**：A—E是54条真人录音构建的控制实验，F才是自然会议截取。两分钟延迟指标来自录音回放；真实麦克风只完成约2.9秒采集链路探测，该次无有效讲话，不能宣称已验证两分钟真人现场识别质量。
- **运行条件**：首次下载需要网络，之后本地推理依赖已下载模型和完整Python环境；GPU还依赖匹配的CUDA/cuDNN。本交付目录附源码和样本，未附模型、虚拟环境和缓存，不能作为免安装程序运行。
- **云端状态**：密钥留空，仅完成接口及本地协议验证；实际上传限制、识别效果、网络延迟、费用和服务响应兼容性仍待真实调用验证。

### 采用建议与后续改进

当前应采用**本地离线转写＋时间戳作为基础结果、说话人离线分析作为辅助标记、近实时文字作为即时预览**的组合。交付02时保留未知标签和原始证据；交付06时按同一片段更新文字并区分partial/final。需要可靠文字时，以保存录音的离线复核结果为依据，仍应核查模型错误。

如继续提升质量，应优先补充自然会议和真人麦克风长时测试，再比较模型大小、改进实时端点检测，并针对短发言与交叠场景调整说话人方案；这些是后续改进方向，不属于本轮已经验证完成的能力。云端密钥配置后，再用同批录音进行真实本地/API对照。
